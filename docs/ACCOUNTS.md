# 账号体系

用户系统（第 5 个系统层）负责身份与账号生命周期。它不产 HTML、不实现令牌签发、不定义权限模型 —— 这三件事分别归主题、安全层、权限层。

## 1. 账号模型

表 `{prefix}user_accounts`（SQL 归 `systems/User/migrations` 自持）：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `username` | 唯一，3~32 位字母 / 数字 / 下划线，不能是纯数字（避免与「按 ID 查找」的标识解释冲突） |
| `password_hash` | `password_hash()` 结果，永不对外返回 |
| `display_name` | 展示名，1~64 字符 |
| `role` | 角色标识，交给权限层解释；`admin` 是内置的管理员角色 |
| `status` | `active` / `disabled` |
| `failed_attempts` | 连续失败次数，登录成功或锁定到期后归零 |
| `locked_until` | 临时锁定截止时间，`NULL` 表示未锁定 |
| `last_login_at` | 最后一次成功登录 |
| `created_at` / `updated_at` | 创建与更新时间 |

## 2. 账号能做什么

自助（主体是自己，`auth=user` 即可，不挂权限点）：

| operation | 说明 |
| --- | --- |
| `auth.register` | 注册并直接签发令牌；受 `user.registration.enabled` 控制，关闭时返回 40304 |
| `auth.password.change` | 校验旧口令后改密，保留当前令牌、吊销其他全部令牌 |
| `auth.logout` | 撤销当前令牌；静态令牌返回 `revoked=false` |
| `users.me.update` | 改显示名；字段白名单只有 `display_name` |

管理（`auth=admin` + `user.read` / `user.manage`）：

| operation | 说明 |
| --- | --- |
| `users.list` | 按状态筛选、offset 分页；SELECT 列表里没有口令摘要 |
| `users.view` | 按数字 ID 或用户名取单个账号 |
| `users.manage` | `disable` / `enable` / `set_role` / `reset_password` |

`users.me`（读取当前身份）与 `users.me.update` 都不声明权限点：把「看自己的身份」交给可编程授权，会让新注册用户登录后连自己是谁都读不到。

## 3. 登录判定顺序

`PdoUserProvider::attemptLogin()` 是 API 登录与页面会话登录的唯一入口，顺序固定：

1. **查账号**。不存在 → 对固定 bcrypt 常量空转一次 `password_verify()`，再返回「口令错」。空转是为了抹平「响应快 = 用户不存在」的枚举信号。
2. **看锁定**。`locked_until > now` → 直接拒绝，不再验证口令（锁定期间不该被用来试探）。
3. **验口令**。失败 → 失败计数 +1；达到阈值则写入 `locked_until` 并把计数清零。
4. **看状态**。`status != active` → 返回「账号已被禁用」。放在口令之后，避免「禁用」变成不需要口令就能探测到的状态。
5. **成功**。清计数、解除锁定、记录 `last_login_at`、签发令牌。

顺序反过来会造成两类问题：先看状态会让禁用状态可被无口令探测；先看口令再看锁定会让锁定形同虚设。

## 4. 口令策略

`CredentialPolicy` 是注册、改密、管理员重置三条路径共用的唯一判断：

- 长度 ≥ 8（配置只能调高，不能调低），≤ 72 字节
- 不能等于用户名（不区分大小写）
- 不能是内置弱口令表里的常见口令
- 不能是单一字符重复（`aaaaaaaa`）或连续键盘序列（`12345678`）

**72 字节上限不是随意定的**：bcrypt 只取前 72 字节作为有效输入，`password_hash()` 会静默截断。超过 72 字节的口令，后半段随便输都能通过 —— 用户以为更安全，实际更弱。因此必须在入口显式拒绝，而不是交给哈希函数悄悄处理。

## 5. 令牌吊销语义

| 场景 | 行为 | 理由 |
| --- | --- | --- |
| 登出 | 撤销当前令牌 | 单枚凭据失效 |
| 改密 | 保留当前令牌，撤销其他全部 | 改密是止损，不该把自己也踢下线；其他设备必须立刻失效 |
| 禁用账号 | 撤销该账号全部令牌 | 否则「禁用」只是登录被拒，手里的令牌照样能调写接口 |
| 管理员重置口令 | 撤销该账号全部令牌 | 原主可能已失去控制 |

实现集中在 `AccountRevocation`。它直接 UPDATE 安全层的 `user_tokens` 表，这是有意识的跨层写：

- 改发 `user.revoked` 钩子让安全层订阅 —— 安全层缺席时钩子静默无操作，禁用变成假动作；
- 每次鉴权 join 账号表查 `status` —— 成本摊到每个请求上。

因此选择在「账号状态变更」这个低频写路径上主动清理，读路径零改动。

## 6. 错误码

| code | HTTP | 含义 |
| --- | --- | --- |
| `40103` | 401 | 账号已被禁用 |
| `40105` | 401 | 用户名或口令不正确 |
| `40304` | 403 | 注册未开放 |
| `40906` | 409 | 会移除最后一个管理员 / 禁用当前账号 |
| `40907` | 409 | 用户名已被占用 |
| `42902` | 429 | 账号已临时锁定 |

`40102`（令牌无效或已过期）只表示「请求携带的令牌有问题」，不再用于登录口令错误。两者分开是因为对外 `message` 直接取自码表：共用 `40102` 会让登录失败的用户看到「令牌无效或已过期」，与发生的事毫无关系。

## 7. 失败模式

| 失败 | 表现 | 是否影响业务 |
| --- | --- | --- |
| 账号表不可用 | 注册 / 登录 / 管理返回 50101 或 50004 | 只影响账号路径，读接口照常 |
| 令牌吊销失败 | 抛异常，不吞 | 宁可让禁用报错，也不让禁用变成假动作 |
| 写入唯一键冲突 | 捕获 23000 → 40907 | 用户可换名重试，不会看到 50001 |
| 显示名非法 UTF-8 | 422 | 拒绝写入，避免后续 `json_encode` 失败导致响应空白 |
| 配置把注册打开 | 注册接口可用；关闭后立即 40304 | 无缓存，改配置即生效 |

## 8. 部署清单

1. **改掉种子口令**：`seed()` 会在空库写入 `admin/admin123`，仅用于本地原型。首次登录后立刻改密。
2. **确认注册开关**：默认 `user.registration.enabled=false`。开放注册前先想清楚是否需要邀请码或审核。
3. **反向代理下的真实 IP**：限流与登录失败计数都以 `clientIp()` 为主键时，必须让代理传递并信任 `X-Forwarded-For`，否则所有请求会共享同一个来源。
4. **锁定窗口**：`user.login.lock_seconds` 默认 900 秒。面向公网的管理后台不建议低于 300 秒。
5. **审计**：`users.manage` 的四个动作都会改变账号状态或凭据，建议在反向代理层保留请求日志（含 `user_id` 与 `action`），便于事后追查。
