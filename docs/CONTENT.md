# 内容互动：评论、附件、表情

> 这份文档回答一个问题：**当内容从「一篇文章」长成「一篇有人讨论、有资料可下载、有表情可表达的文章」时，系统层该怎么切。**

三个系统层（`comment`、`attachment`、`emoji`）不是三个功能模块，而是三组**不同所有权的数据**：

| 系统层 | 拥有的东西 | 不拥有的东西 |
| --- | --- | --- |
| `comment` | 评论之间的关系、审核状态、可见性 | 文章正文、用户资料、页面样式 |
| `attachment` | 文件元数据、字节的存放与取用 | 文章是否该引用它、表情是否该用它 |
| `emoji` | 短码与字形 / 图片的映射 | 图片字节、正文内容、渲染标签 |

边界划在这里，是因为它们的**生命周期不同**：文章删了，评论该跟着走；附件可能被多篇文章、评论、表情同时引用；表情删了，历史正文必须原样保留。把三者塞进 `content` 会得到一个「删文章顺手删了别人头像」的系统。

---

## 1. 评论：树不是列表

### 1.1 为什么不是五个并列状态

评论的难点从来不是「存一条文本」，而是三件事同时成立：

1. **关系**：谁回复谁，深度多少，删了父评论子回复还在不在；
2. **可见性**：待审的只有作者和管理员看得到，垃圾只有管理员看得到；
3. **可变性**：作者能删自己的，版主能删任意，删了要能恢复对话结构。

### 1.2 结构：邻接表 + 物化路径

| 方案 | 写入 | 读整棵树 | 取子树 | 本项目 |
| --- | --- | --- | --- | --- |
| 纯邻接表（只有 `parent_id`） | 简单 | 需递归 CTE | 需递归 | 不够 |
| 纯物化路径（只有 `path`） | 要预知 id | 排序有位数陷阱 | 前缀查询 | 不够 |
| 闭包表 | 复杂 | 简单 | 简单 | 过重 |
| **邻接表 + 路径 + 深度** | 一次 INSERT + 一次回填 | 应用层一次遍历 | 前缀查询 | **采用** |

`path` 形如 `/12/45/98/`，`depth` 单独存一列避免每次数字符。但**树序不按 path 字符串排序**：路径段位数不等时字典序会把 `10` 排到 `2` 前面。树序由父子关系决定，同层按 `id` 升序（即时间顺序）。

写入分两步：先 INSERT 拿到自增 id，再回填 `path` 与 `root_id`。这不是「两次写」的妥协，而是自增 id 与路径的必然依赖；两步在同一请求内完成，失败即整条回滚（由数据库事务保证）。

### 1.3 深度上限：拒绝，而不是静默改挂

超过 `comment.max_depth`（默认 5）时，本项目**拒绝**并给出明确提示，而不是像部分实现那样「自动挂到最深祖先」。

理由是第一性原理里的「不静默改变用户意图」：用户点了「回复 A」，系统却把评论挂到 B 下面，界面上看不出差别，对话语义已经错了。拒绝会让人不爽一次，静默改挂会让人困惑一辈子。

### 1.4 软删：tombstone 保住对话链

删除**不清行**：

| 字段 | 删除后 |
| --- | --- |
| `status` | `deleted`（终态） |
| `body` | 空字符串 |
| `author` | 空字符串 |
| `deleted_at` | 删除时间 |
| `parent_id` / `path` / `root_id` | **保留** |

于是「A 说了一句被删的话，B 回复了它」仍然渲染成：

> **该评论已删除**
> └─ B：你说得对

硬删会让 B 的回复变成孤儿，或被提升到根节点，两种结果都在篡改对话。已删除的评论**不再接受新回复**——占位节点不是有效对话对象，但它的子节点照常显示。

重复删除是幂等的：第二次返回 `deleted=false, already=true`，不报错、不重复改库。

### 1.5 审核：显式白名单状态机

```
pending ──→ published / hidden / spam
published ─→ hidden / spam
hidden ───→ published / spam
spam ─────→ hidden / published
deleted ──→ （终态，不可迁入也不可迁出）
```

非法迁移返回 `40901`。白名单集中在 `CommentPolicy::TRANSITIONS`，不散落在各接口里——散落的 `if` 迟早会漏掉一条路径，让「已删除的评论被审核回来」。

### 1.6 可见性由身份与事实推导

| 状态 | 匿名 | 作者本人 | 管理员 |
| --- | --- | --- | --- |
| `published` | 可见 | 可见 | 可见 |
| `pending` | 不可见 | 可见 | 可见 |
| `hidden` | 不可见 | 可见 | 可见 |
| `spam` | 不可见 | 不可见 | 可见 |
| `deleted` | 占位 | 占位 | 占位 |

这张表不落库，每次由 `status + identity + ACL` 算出来。落库就会漂移。

### 1.7 反垃圾：入口守卫，不是事后清理

`CommentGuard` 在入库前做四件事：统一换行、剔除控制字符（零宽字符与退格能让同一条评论「看起来一样、字节不同」，既绕过重复检测，也能伪造排版）、长度上限、链接数上限。

三条都不通过就 `42201`，不做「先收下再悄悄隐藏」——后者会让用户以为发出去了。

## 2. 附件：文件不是一行

### 2.1 元数据与字节分离

| 层 | 存什么 | 存在哪 |
| --- | --- | --- |
| 元数据 | 展示名、MIME、字节数、哈希、可见性、上传者 | `wx_attachments` 表 |
| 字节 | 文件内容 | `storage/attachments/<aa>/<bb>/<sha256>` |

分开的直接收益：**删一条记录不会删掉别人的文件**。同一份字节可以被多篇文章、多个表情引用，元数据各自独立成行，删除只是把某一行的 `deleted_at` 填上。字节回收由「引用计数为 0」的独立流程决定，不在请求路径里做文件系统删除。

### 2.2 内容寻址：文件名不进路径

存储路径完全由 SHA-256 生成，原始文件名只作为展示名存在库里。这一条决定同时解决了四类经典问题：

| 攻击 | 为什么失效 |
| --- | --- |
| 路径穿越 `../../etc/passwd` | 文件名根本不参与路径 |
| 双扩展名 `shell.php.jpg` | 落盘文件没有扩展名 |
| 同名覆盖 | 不同内容 → 不同哈希 → 不同路径 |
| 上传目录被当脚本执行 | 目录在 webroot 外，文件无扩展名，且 `.htaccess` 关闭引擎 |

展示名仍要净化，但净化方式是**取最后一段**（`basename`）而不是「把斜杠删掉」：`../../etc/cover.png` 若删斜杠会变成 `etccover.png`，看似安全、语义已错。

### 2.3 四道校验，缺一不可

| 顺序 | 校验 | 挡住什么 |
| --- | --- | --- |
| 1 | 大小上限（默认 8 MiB） | 拖垮内存与磁盘的巨型文件 |
| 2 | 扩展名白名单 | 可执行、可渲染类型（`php` / `html` / `svg` / `js` 一律不在名单） |
| 3 | 魔数匹配 | 改名冒充：`not-a-png` 改成 `.png` |
| 4 | 配额（单文章附件数） | 单篇塞满磁盘 |

**不读客户端声明的 `Content-Type`**：它由请求方自由填写，只能当提示，不能当证据。对外 MIME 只从白名单表取。

文本类（`txt` / `md` / `csv`）没有魔数，改用「无 NUL 字节 + 合法 UTF-8」判定——同样能挡住改名的可执行文件。

### 2.4 二进制通道：唯一不经 JSON 信封的出口

上传 `POST /attach/upload`、下载 `GET /attach/download`。它们不是「另一套接口」，而是**同一个 registry 里的两个 operation**，由 `AttachmentBinary` 执行、`AttachmentRoute` 做 HTTP 适配。

守卫完全复用：

```
限流 → 写接口公网边界 → 鉴权 → 权限 → 参数校验
```

这一步是刻意的：文件上传是最容易被单独「优化」出一条旁路的地方，而旁路一旦存在，前面所有的鉴权都白做了。

### 2.5 下载也要授权

「URL 猜不到」不是访问控制。每次下载都过 `visibility` 判定：

- `public`：任何人可下；
- `private`：必须登录，且是上传者本人或有 `attachment.read`。

响应头三件套：

```
Content-Type: <白名单 MIME>
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; sandbox
```

即使字节被调包成 HTML，浏览器也不会在本域执行它。`Content-Disposition` 同时给 ASCII 回退名与 RFC 5987 的 `filename*=UTF-8''`，中文名不会乱码，也不会因引号截断头部。

## 3. 表情：注解，不是替代

### 3.1 三种来源，一种身份

| 类型 | 例子 | 存储 |
| --- | --- | --- |
| Unicode | `:smile:` → 😄 | 代码里的内置表 |
| 颜文字 | `:shrug:` → `¯\_(ツ)_/¯` | 同上 |
| 图片 | `:shipit:` → 本站 PNG/GIF | `wx_emojis` + 附件 |

对解析器而言它们只有一种身份：一个稳定短码对应一个可渲染值。

### 3.2 产出 token，不产出 HTML

`EmojiParser::parse()` 返回：

```php
[
  ['type' => 'text',  'value' => '你好 '],
  ['type' => 'emoji', 'code' => 'smile', 'kind' => 'unicode', 'value' => '😄', 'alt' => ':smile:'],
]
```

主题拿到 token 才决定画成文字还是 `<img>`。系统层零标签（规矩 B/J），主题仍是唯一有权写 HTML 的地方。

### 3.3 存原文，渲染时解析

表情删除后，历史正文里的 `:shipit:` 会退回字面量，而不是变成空白。这是「存原文」相对「入库即替换」的关键收益：

- 改一个短码的映射，不需要重写历史；
- 删一个表情包，不会毁掉旧评论；
- 内容仍可被检索、diff、导出。

### 3.4 自定义表情只引用本站附件

`emojis.register` 只接受 `attachment_id`，**拒绝任何 http(s) 外链**。

外链表情有两个问题：浏览者的每一次浏览都会向第三方发请求（追踪像素），且图片内容可被随时替换。把图片收进本站，等于把这块攻击面关上。读取时也只生成 `/attach/download?id=N`，库里即使被写入外链也不会被渲染。

### 3.5 边界：未知短码保持字面量

正则带边界断言 `(?<![\w:]):([a-z0-9_+-]{2,32}):(?![\w:])`，因此：

- `http://127.0.0.1:8080/x` 不会被解析成表情；
- `a:smile:b` 不会；
- `:not_a_real:` 原样显示。

「不认识的就不动」比「尽力猜测」更安全，也更诚实。

## 4. 三者如何协作

```
content ──(slug)──→ comment ──(emoji.parse)──→ emoji
                                  │
                                  └──(attachment_id)──→ attachment
```

| 协作 | 方式 | 为什么不是直接依赖 |
| --- | --- | --- |
| 评论校验文章存在 | `ContentRepositoryInterface::findBySlug` | 只认契约，不认 PDO 实现 |
| 文章 / 评论接入表情 | `emoji.parse` 过滤器 | 内容层不认识表情层；没有表情系统时退化为纯文本 |
| 自定义表情引用图片 | `AttachmentRepositoryInterface::find` | 表情层不碰文件系统 |

`comment` 的 `system.json` 声明 `requires: ["log","security","content"]`，`emoji` 声明 `requires: [..., "attachment"]`。装配顺序由依赖拓扑决定，不靠 priority 硬排：

```
… api → state → plugin → member → content → release → theme → attachment → emoji → comment → page
```

## 5. 与状态系统的关系

评论提交失败时，文章页返回的状态信封复用第 15 层的五态：

```php
['phase' => 'failed', 'code' => 40301, 'title' => '评论未提交',
 'message' => '表单已过期，请刷新后重试', 'hint' => '修改后可以直接重试，已填写的内容仍在表单里。']
```

状态系统负责「这次操作为什么失败、下一步做什么」；评论系统负责「这条评论存在哪、谁能看」。两者不互相替代。
