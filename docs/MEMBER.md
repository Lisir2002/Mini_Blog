# 成员成长页（`/console/member`）

> v0.41 补「看见」：等级表 / 头衔目录 / 经验规则 / 排行榜 / 单人档案，并修掉两个自洽但错误的数。
> v0.42 补「改动」：五个写接口接进操作台，成功 303、失败绝不跳转，结果按实际发生的事回报。

## 1. 为什么先只读、再分开做写

成员系统从 v0.10 起就有十个接口，页面一个都没调过。读者不知道自己为什么是 Lv.2，
站长不知道自己定义的头衔还在不在 —— 这是「看见」的问题。

写事的复杂度不在表单，而在语义：发经验的重复提交、没配规则时 `amount` 从哪来、
授予一个不存在的头衔、改门槛会不会影响所有人、删定义要不要确认。
v0.41 只做只读，v0.42 单独做写，每条都留够解释与守卫的篇幅。

## 2. 接口语义（v0.41 修正）

### 2.1 `member.leaderboard`

| 字段 | 含义 | 易错点 |
| --- | --- | --- |
| `total` | **有成长档案的成员总数** | 原先返回本页条数（`array_slice` 之后 `count()`），拿它写「共 N 人」永远成立且不报错 |
| `returned` | 本页返回条数 | 与 `total` 一起看才知道看的是第几页 |
| `has_more` | 后面还有没有下一页 | 分页界面需要的是这个，不是自己拿两个数去减 |
| `next_offset` | 下一页的 offset，没有则 `null` | 页面直接用它拼链接，避免各页面自己算上限 |
| `items[].orphan` | 该条目解析不到账号 | 账号被删，或档案是按 `user_id` 直接写入的 |

`count()` 来自存储协议（`ProfileStoreInterface::count()`，PDO 走 `SELECT COUNT(*)`，内存实现走数组长度），
与 `leaderboard()` 同表同口径 —— 两个数各算一套是下一处漂移的来源。

### 2.2 `member.profile`

原先只对**非数字**标识返回 `40403`，于是 `?user_id=999999` 走进「按 ID 直接组装」分支，
返回 `xp: 0 / level: 1 / username: ""`，HTTP 200。一份看起来正常的空档案会让人以为这个人真的存在，
进而给他发经验、授头衔 —— 而 `member.xp.award` 确实不校验账号存在，库里就多一条没人能认领的档案。

现在：**用户与档案都查不到**才 `40403`；档案在而账号查不到，返回档案并置 `orphan: true`。
读路径收紧、写路径放宽是刻意的 —— 界面不能把人指错，但插件可以给站点外主体记账。

## 3. 权限：读一个点，写五个点

成员层自报的权限点在 v0.41 前全是写。一个只读视图只有两条路：借写权限点（等于说「能看 = 能发」），
或者不声明（审计时看不出这一页归谁）。v0.41 补 `member.read`（48 → 49 个权限点），
与 `user.read` / `permission.read` / `logs.read` 对齐。

**接口不跟着收紧**：等级表与头衔目录本来就该对读者公开。经验规则例外，按 `member.xp.rule.manage` 裁剪，
且页面**先问决策器、再决定调不调** —— 调了再吞 403 会把「你没权限」与「接口坏了」混成同一句失败。

v0.42 的五个写动作各自问自己的写权限点：

| 动作 | 接口 | 权限点 |
| --- | --- | --- |
| 发放经验 | `member.xp.award` | `member.xp.award` |
| 经验规则 | `member.xp.rule` | `member.xp.rule.manage` |
| 头衔定义 | `member.title` | `member.title.manage` |
| 授予头衔 | `member.title.grant` | `member.title.grant` |
| 等级定义 | `member.level` | `member.level.manage` |

页面直调执行者会绕过 API 分发器的权限检查，所以这五次裁决在 `MemberAction` 里现场做，缺席即 403。
**票据按页面级的 `member.read` 签发**，只证明「谁从哪一页交的」，不替代任何一次写裁决 ——
这正是 58 组里「只给 `member.xp.award` 时能发经验、改规则仍 403」要证明的事。

## 4. 四种「没有」必须分开

| 状态 | 触发条件 | 页面呈现 | 为什么不能合并 |
| --- | --- | --- | --- |
| `empty`（榜） | `total = 0` | 「还没有人获得经验」+ 解释榜单只含有档案的人 | 说成「站点没有成员」是错的：账号在 `/console/users` |
| `permission-denied` | 无对应权限点 | 「看不到经验规则」/「没有 XX 的权限」 | 把「看不到」读成「没有」会让站长去建重复规则 |
| `unconfigured` | 等级表为空 | 「等级表是空的」+ 说明所有人会被解释成 Lv.1 | 空表时页面一切正常，没人能升级也没有报错 |
| `inconsistent` | 等级跳号 / 门槛重复 | 「等级表有断点」+ 指出缺哪一级 | 接口层认为合法，成员却会卡在同一档 |
| `unavailable` | 接口抛错 / 成员层停用 | 逐块降级，错误原文照给 | 读不到不能长得像「没有」 |

## 5. 页面结构

1. **范围说明** —— 上面看现状、下面做改动；
2. **结果 / 失败提示条** —— 成功 303 回来说实际发生了什么；失败留在原页，不跳转；
3. **操作台** —— `?panel=` 切换五个动作，一次只渲染一张表单；
4. **等级表** —— 档位 / 门槛 / 颜色，附断点告警；
5. **头衔目录** —— 显式 `include_hidden=1`，隐藏项标「隐藏」并计数；
6. **经验规则** —— `+50 / 次 · 每日上限 200 · 说明`；`daily_cap = 0` 显示成「不限（0）」；
7. **排行榜** —— 名次窗口、上/下页、`orphan` 行标注、翻过末尾的单独说明；
8. **单人档案** —— `?user=` 查询，查不到说「用户不存在」；
9. **出口与边界** —— 去用户 / 角色 / 决策 / 内容，以及榜单口径与分页口径。

## 6. 操作台（v0.42）

用 `?panel=` 切换而不把五张表叠在一页：五个动作共二十多个字段，叠在一起只能靠 placeholder
猜「哪些格子对这次提交生效」。切换后每张表单的字段就是它真正会提交的全部参数，
且不依赖脚本、可收藏、可回退。切换链接保留 `user` / `offset`，不会丢掉正在看的上下文。

三条硬规则：

- **`op` 只能由提交按钮给出**。缺失或未知一律 422 —— 默认成 `upsert` 等于让「没点按钮的请求」悄悄改配置；
- **删除定义类配置要手写主键确认**（`confirm` 逐字等于 `action` / `title_key` / `level`）。
  「保存 / 新建」与「删除」两个按钮并排，误点没有撤销机会；
- **没权限或票据签不出来就不渲染表单**，明说原因。渲染一个点了必然 403 的按钮比没有更糟。

表单字段的 hint 与 `MemberInput` 的校验规则一一对应；两处必须同时改，
「表单说可留空、校验说必填」是最容易被忽略的静默出错。

## 7. 结果回报：五种 outcome，不是一句「已发放」

`member.xp.award` 的「成功」有五种不同含义，一律回「已发放」等于骗人：

| outcome | 触发 | 页面说 |
| --- | --- | --- |
| `applied` | `applied > 0` 且无显式部分截断 | 给谁加了 N 分，当前余额 / 等级 / 是否升级 |
| `duplicate` | `reason = duplicate` | 这个 `event_key` 已记过账，本次没有重复加分（幂等在生效，不是失败） |
| `daily_cap` | `reason = daily_cap` | 今天已达上限，本次加 0 分（接口按设计截断，不报错） |
| `disabled` | `reason = disabled` | 规则被停用，本次加 0 分 |
| `truncated` | 显式 `amount=10`、`applied=3` | 实际只加了 3 分，另外 7 分被每日上限截断 |
| `no-change` | `changed = false` | 本来就是这个值 / 本来就已授予 / 本来就没有 / 目标本来就不存在 |

`changed=false` 单独分场景：`upsert` 幂等、删不存在的定义、重复授予、撤销本来就没有的授予，
四种处置方式完全不同。一句「没有变化」会让管理员分不清是重复提交还是写错了标识。

`event_key` 由人填而不是页面自动生成：它标识「同一件业务事实」，管理员必须看得见、能重放。
页面在 hint 里写明「同一个键不会重复加分，想再发一次请换一个键」。

## 8. 页面层挡住 / 说清的三类脏数据

1. **授予目录外的 `title_key`** —— `TitleBook::grant()` 只校验 `user_id` 非空，
   写错的标识会落一条关系，档案里永远看不到，且不报错（与 `permission.grant` 同类）。
   页面先调 `member.titles`（`include_hidden=1`）核对，读不到目录就 fail-closed 拒绝；
2. **删除定义不写确认** —— 接口 `op=delete` 直接删，页面要求手写主键；
3. **给既无账号也无档案的 ID 发经验 / 授头衔** —— 写路径放宽是刻意设计（插件可给站点外主体记账），
   所以**不拦**，但提交前查一次 `member.profile`，40403 时在结果里明说「这次会凭空建一份没人能认领的档案，
   排行榜上会多一行空名字」；`orphan=true` 时明说「档案在，账号查不到了」。

另有一条「接口不管、页面必须翻译」的失败：没有规则又没填 `amount` 时，系统层抛的是
`InvalidArgumentException('未配置该动作的经验规则，需显式传入 amount')`。页面把它翻成
「要么在经验规则里定义它，要么在本次表单里显式填 amount」，而不是丢一句通用 422。

## 9. PRG 与方法边界

成功一律 **303** 回本页：既不因刷新重复提交，也让管理员立刻看到改完之后的等级表 / 规则 / 榜单。
**失败绝不 303**：表单里的输入原样回填，否则一次手误就得把二十个字段重新填一遍。
结果参数只带 `saved` / `op` / `key` / `outcome` / `changed` / `detail` / `hint` / `panel`，
不把票据、备注、经验值留在地址栏。

方法边界：非 GET 且无票据的请求一律在守卫层 401（Cookie 不参与写，v0.9 起的 CSRF 边界）；
已认证的 `PUT` / `DELETE` 返回 `405` + `Allow: GET, HEAD, POST`；
`POST` 走带票据的表单提交（Bearer 身份同样可用，但 Action 仍逐动作问权限）。

## 10. 消费矩阵的一处误报（v0.42 修正）

`tools/consumers.php` 把「字符串字面量里出现过 operation 名」记为 `ref`，用于识别动态拼接的调用。
但 member 系统六个**权限点与 operation 同名**，于是 v0.41 的 `MemberQuery::capabilities()` 里
`$acl->allows($identity, 'member.xp.award')` 被当成「已经有人发经验」——
两个写接口被假消费掩盖，零消费清单里永远看不见它们。

修法：扫字符串前先把 `->allows(...)` / `::allows(...)` 调用整段抹掉。
字符串字面量只能证明「提到过」，这里是唯一能明确判否的上下文。
`49-consumers.php` 增加两条回归断言（净化逻辑存在、只读页不再被算成写接口消费方）。

## 12. 边界

- 不做批量写、不做经验流水查看（流水在 `member_xp_events`，接口没开）；
- 不做游标分页：榜单变动时 offset 会漏行或重行，已在页面上写明；
- 定义类删除只改解释规则，不清理已落库的手动授予关系；
- 不做头衔与权限的联动：头衔不产生任何权限，这是 v0.10 起的刻意设计；
- 不做「影响面预览」：改等级门槛会影响所有人的下一次读取，页面只说明，不预演。
