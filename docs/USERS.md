# 用户管理

`/console/users` 把「授权只能靠 curl」变成站点上能完成的事：列表、禁用 / 启用、改角色、重置口令。

## 1. 读与写是两道权限

| 能力 | 需要的权限点 | 由谁判定 |
| --- | --- | --- |
| 看列表 | `user.read` | 页面守卫（page.json 声明） |
| 禁用 / 启用 / 改角色 / 重置口令 | `user.manage` | `UsersAction` 在调用前再判一次 |

页面只声明 `user.read`。能看列表不等于能改账号：没有 `user.manage` 时只渲染只读表格，
不渲染点了必然 403 的按钮；即使有人手工构造 POST，`UsersAction` 也会 fail-closed 拒绝。

**为什么页面还要自己判一次**：页面直接调执行者，绕过了 API 分发器的权限检查。不补这一道，
`user.read` 就会悄悄等于 `user.manage`。

## 2. 防呆不变量

两条规则由账号层抛出 40906，页面只原样呈现：

- 不能禁用当前登录的账号 —— 否则管理员点一下就把自己关在门外；
- 不能移除最后一个管理员 —— 否则站点再没有任何账号能进管理端。

页面**不复制**这两条判断：复制就会有两套规则，迟早分叉。禁用与重置口令都会撤销该账号
全部令牌，否则「禁用」只是登录被拒的假动作。

## 3. 操作与结果

| 动作 | 成功 | 失败（页面留在原处） |
| --- | --- | --- |
| `disable` | 303 + 「已禁用，令牌已撤销」 | 40906 自己 / 最后一个管理员 |
| `enable` | 303 + 「已启用」 | 40403 账号不存在 |
| `set_role` | 303 + 「角色已更新」 | 42201 角色名非法；40906 改自己 |
| `reset_password` | 303 + 「口令已重置」 | 42201 口令策略不通过；40906 最后一个管理员 |

失败不 303：303 是「去看另一个地址」，失败必须留在原地说明原因。

## 4. 列表

- 默认每页 50 个，`offset` 翻页；被截断时明确写「未列全」并给下一页链接；
- `status=active|disabled` 筛选，未知值回落为「全部」而不是报错；
- 空列表与读取失败长得不一样：前者 200 + 「没有账号」，后者 200 + 「列表不可用」+ 原因；
- 没有 `user.manage` 时渲染只读表格（id / 用户名 / 角色 / 状态 / 创建时间），不显示表单。

## 5. 不做的事

- 不做新建账号：注册与管理员建号是两条不同路径，后者还需要邀请 / 初始口令策略；
- 不做删除账号：账号与内容、评论、令牌有引用，删除需要先定义「内容归属转移」；
- 不做批量操作：一次误点影响多个账号，收益不抵风险；
- 不做权限点编辑：那是 `permission.*` 的界面，权限接口仍未接，属于独立一版。
