# 内容生命周期与分类体系

> 代码：`systems/Content/`；接口：`API-CONTENT-001 … 013`；守卫：`tests/groups/36-content-lifecycle.php`。

v0.27 之前，内容层只有「读、写、改」三件事，且都是半成品：`ContentRepositoryInterface`
没有删除方法，文章一旦写进去就永远删不掉；`status` 是不受约束的字符串，
`content.create` 传什么就存什么。于是写错一个状态值 → 文章从所有列表里消失 →
创建接口返回成功 → 站长以为自己没保存。

这一轮补齐三件事：**状态机、回收站、分类与标签**。

## 1. 状态机

四个状态，迁移边是穷举的：

| 从 \ 到 | draft | review | published | archived |
| --- | --- | --- | --- | --- |
| **draft** | 幂等 | ✅ | ✅ | ✅ |
| **review** | ✅ | 幂等 | ✅ | ✅ |
| **published** | ✅ | ❌ | 幂等 | ✅ |
| **archived** | ✅ | ❌ | ✅ | 幂等 |

两条边被刻意禁止：**published → review** 与 **archived → review**。
已发布内容「退回审核」没有业务含义 —— 真要重审，先下架（→ draft），
动作与意图一致，日志也能读。

两种错误必须分开：

| 情况 | 码 | 为什么不是同一个 |
| --- | --- | --- |
| `status=publiched`（拼错） | `42201` | 客户端改一下就能成功，重试有意义 |
| `published → review`（不可达） | `40908` | 重试永远不会成功，得先做别的动作 |

混成一个码，前端只能显示「保存失败」，用户会一直点同一个按钮。

**同状态迁移是幂等成功**，不是冲突。双击「发布」不该报错 —— 但也不能靠
`rowCount` 判断：MySQL 在「值没变」时同样返回 0。所以 `transition()` 在
`rowCount === 0` 时回读一次，确认当前状态是否已经是目标状态：

```php
if ($stmt->rowCount() > 0) return true;
return (string) ($this->findBySlug($slug)['status'] ?? '') === $to;
```

**并发是「比较并设置」**：`UPDATE ... WHERE slug = ? AND status = :from`。
两个人同时把同一篇草稿分别改成「已发布」和「已归档」，后到的那个收到 `40908`，
而不是静默覆盖前一个人的动作。

## 2. 回收站

`deleted_at` 与 `status` 正交，不是第五个状态。原因很实际：
回收站里的文章仍然记得它是草稿还是已发布，恢复时才能回到原位。
把「已删除」做成状态，恢复就得猜它原来是什么。

| 动作 | 状态 | 可见性 | 说明 |
| --- | --- | --- | --- |
| 软删除 | 不变 | 列表 / 详情 / 计数全部消失 | 只打 `deleted_at`，不重复计时 |
| 恢复 | 不变 | 回到删除前的可见性 | 不顺手改成已发布 |
| 彻底删除 | 行消失 | 不可恢复 | 只对回收站里的文章生效 |

两条防呆：

- **重复删除返回 `40909`**，而不是再删一次。否则「删除时间」会被一次次刷新，
  保留期永远不到，回收站变成永久仓库。
- **彻底删除必须回写 slug**（`confirm` 与 `slug` 完全一致）。布尔值会被前端默认勾上；
  写 slug 是没法顺手点过去的动作，代价刚好等于这件事的不可逆程度。
  同时在展示中的文章必须先删除再彻底删除 —— 手滑与决定之间隔一个动作。

## 3. 定时发布

`publish_at` 是读路径判定的，不是定时任务：

```sql
status = 'published' AND (publish_at IS NULL OR publish_at <= :now)
```

没有 cron 的站点也得在到点那一刻自动可见。反过来，判断必须一致：
**未到点的文章不计入 `published` 计数**，否则首页写「共 12 篇」而列表只有 9 篇。

只在列表里过滤还不够：知道 slug 的人照样能提前读到，排期就失去意义。
所以 `content.post` 对未到点的文章返回 `40403` —— 与「不存在」同一个码，
因为**对外部世界它就是不存在**。

`publish_at` 只对 `published` 有意义。改成草稿时会被清空，避免留下
「已经退回草稿、却还排着明天早上八点」的残留。

## 4. 分类与标签

一张术语表 + 一张关系表，用 `kind` 区分：

```
content_terms            (id, kind, slug, name, description, ...)
content_term_relations   (post_id, term_id, created_at)
```

**为什么不是两张表**：两者的读写路径完全相同（slug / 名称 / 多对多绑定）。
拆成两套会得到两份几乎逐字相同的 SQL，将来修一个缺陷要记得改两处。

**为什么没有外键**：表前缀是多站点隔离手段，而外键名是 schema 级唯一，
同一库里两个前缀会撞名。孤儿由 `RelationRegistry` 登记 + `php tools/data.php verify`
巡检；删除术语时在事务里显式清理关系。

三条约定：

1. **绑定只接受已存在的术语**（`kind:slug`）。自动创建更省事，代价是把拼写错误
   变成站点上的新词条：写 `tag:javascrpit` 也能成功，只是那个标签永远只有一篇，
   而且没有任何地方会报错。
2. **一次请求里只要有一个引用不存在，整个操作失败**（`40404`）。部分成功会让
   调用方无法判断到底绑上了哪些。
3. **整体替换而不是追加**：幂等键就是最终的术语集合。

需要 MySQL。内存降级（拔库）时相关接口返回 `50101`，而不是空数组 ——
「还没有标签」和「这个功能在当前部署下不可用」不能长得一样。

## 5. 列表与置顶

`pinned` 与 `sort_weight` 不进主列表的排序。keyset 分页的键是 `id`，
若把 `pinned` 排进主序，两次翻页之间有人置顶，就会出现「第 2 页重复第 1 页」
或整篇被跳过。置顶单独用 `pinned=1` 取，按权重倒序，不分页。

`total` 与 `items` 必须同口径：`total` 用与列表相同的 `WHERE` 单独计数，
游标只影响「这一页从哪开始」。否则按标签筛选后会显示「共 12 篇」却一条也翻不到。

## 6. 已知边界

- **`status` 只在应用层校验**，没有加数据库 CHECK 约束：约束名是 schema 级唯一的，
  多前缀共用一库会撞名。绕过应用直接写库仍可能写入非法值，那类行不会被任何列表
  读到，也不能被状态机迁移（`canTransition` 对未知状态返回 false），需要人工确认。
- **回收站没有自动过期清理**。保留期涉及「删了还能不能找回」的承诺，
  由站点主决定，不做默认动作。
- **分类不限制单选**。一篇文章可以属于多个分类；如果业务需要主分类，
  约束加在业务层，而不是靠拆表来暗示。
