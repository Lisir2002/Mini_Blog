# 性能治理（v0.15）：核心不设计「性能强化系统」

> 一句话结论：**不新增第 18 层，`core/` 零改动。**
> 用户设想的三件事——动态分配核心、CPU 性能调度、线程调度——全部属于**部署层与内核**，不属于应用代码。
> 应用层能负责、且能拿出证据的是「传输经济 + 可观测 + 预算留痕」，做成一个**可装卸、默认关闭**的增强包。

---

## 0. 先回答「有没有必要针对这个方面设计」

**有必要针对「性能」设计，但不该按「服务器动态调核」这个方向设计成系统层。**

这个区分不是文字游戏。v0.14 判断「数据系统」时用的是同一组三问，那次三条都成立，于是把第 8 层原位升级为 `data`；这次三条**全不成立**：

| 判据 | 问的是什么 | 数据层（v0.14） | 性能强化（v0.15） |
| --- | --- | --- | --- |
| 独立生命周期 | 会随**应用**单独演化吗？ | ✅ 换驱动 / 读写分离 / 换巡检策略都只动这一层 | ❌ 随**部署环境**演化：换机器、改容器配额、换 FPM 配置，值就变；代码不该跟着变 |
| 跨系统被依赖 | 各层都要调用它吗？ | ✅ 12 个仓储都走 `DatabaseInterface` | ❌ CPU 配额不是「被调用的能力」，是**环境事实**；没有哪个业务层会 `resolve()` 一个「核心分配器」 |
| 可整体替换 | 换掉实现而不动业务吗？ | ✅ 走契约，内存实现可顶上 | ❌ 换不掉内核调度器；而把它「关掉」业务语义完全不变——这说明它**没有契约**，只是属性 |

> 判据的来源：权限之所以是第 12 层（规矩 K），是因为它横切所有层且**缺席会改变「能不能做」**。
> 性能缺席只改变「多快」，不改变任何结果。**改变语义的才配有一层，只改变快慢的不配。**
> 若硬开一层，它要优化谁就得懂谁，必然认识所有层的内部，直接撞上规矩 S 的「一件事一个主人」与规矩 H 的职责预算。

**还有一条更硬的约束**：`core/` 已是 24/24 文件（规矩 D 已达上限）。性能若要进核心，第一件事就是破预算——而核心变胖正是第一性原理被破坏的第一个信号。

## 1. 为什么「动态分配核心 / CPU / 线程」在 PHP 下不成立

不是「实现成本高」，是**方向错了**。四条事实，全部能在本项目里复核：

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | 应用不持有线程、不持有长驻 worker | `Kernel::handle()` 每请求重建；`ARCHITECTURE.md` §23.4 记录了 `php -S` 冒烟的真实结果 `hits=0 / misses=3 / flushes=0`——进程内缓存**只在单次请求内**生效。跨请求的东西根本不在应用手里 |
| 2 | worker 由 FPM master 管理并回收 | 应用进程调 `sched_setaffinity()` 绑的是「即将被回收的进程」；容器内还需要 `CAP_SYS_NICE`。绑了也不归自己 |
| 3 | 线程调度是内核职责 | PHP 没有用户态线程；要常驻线程池就得引 Swoole / RoadRunner / ext-parallel，全部被**规矩 B**（纯原生栈）挡住 |
| 4 | 「按 CPU 核数动态分配」会读错数 | 本机 `nproc` = **32**，但 `/sys/fs/cgroup/cpu.max` = **`400000 100000`**（配额 **4 核**）。应用若按 32 开 worker，就是 32 个进程抢 4 核配额，上下文切换反而把 P95 拉高 |

**「动态」本身常常是稳定性的敌人**：FPM 的 `pm = dynamic` 会在负载变化时反复 fork / exit worker，带来冷启动与延迟抖动；生产更常用 `pm = static` 配固定 worker 数。也就是说，用户想用「动态分配」换稳定，实际拿到的多半是相反的东西。

> 这不是说服务器配置不重要——恰恰相反，它**很**重要，只是它的正确位置是部署清单与运维动作，不是 `systems/`。第 3 节给出清单，第 7 节给出真实对照数据。

## 2. 分工：一件事只有一个主人

| 层 | 谁负责 | 具体内容 | 在项目里的位置 |
| --- | --- | --- | --- |
| **部署层** | 运维 / 容器 / 内核 | FPM worker 数、`opcache`、CPU 配额、绑核、文件描述符、MySQL 连接数 | `docs/PERFORMANCE.md` §3 的**清单**（文档，不是代码） |
| **应用层（既有）** | 各归属系统自己 | 批量取数 `findMany/parseMany`、游标分页、附件内容寻址、结构指纹免重放 DDL、进程内权限缓存 | `systems/*`，v0.13 / v0.14 已落地 |
| **横切边界** | 规矩 + 守卫 + 工具 | 性能预算、可观测、可重跑基准、开关语义等价 | `CONVENTIONS.md` 规矩 T、`tests/groups/22*`、`tools/bench.php` |
| **可选增强** | 可装卸包 | ETag / 304 / gzip、`Server-Timing`、预算留痕 | `plugins/Performance/`（**默认关闭**） |

关键取舍：**没有把「性能优化」抽成一个框架级能力**。真正的通用优化器必须知道每张表、每个查询、每种响应，立刻变成上帝对象（同 v0.14 拒绝通用仓储的理由）。优化留在归属系统里，统一的是**度量口径与边界**。

## 3. 部署层清单（写清楚，但不写进代码）

以下每项都是「改配置 / 改编排」的动作。**本项目刻意不在运行时读取或改写它们**——应用读 `nproc` 会读到 32 而实际只有 4 核配额，这类「应用自作聪明」正是要消灭的故障源。

| 项 | 建议 | 理由 / 反例 |
| --- | --- | --- |
| `pm.max_children` | 按 **CPU 配额 × 1.5~2** 估，压测后定；不是按可见核数 | 4 核配额开 32 个 worker → 争抢与抖动 |
| `pm` | 生产优先 `static` | `dynamic` 的 fork/exit 抖动；「动态分配核心」不具可重复性 |
| `opcache.enable` / `validate_timestamps` | 开；生产关时间戳校验，部署后统一重置 | 每次请求重编译 PHP 文件是纯浪费 |
| 容器 `cpu.max` / `cpuset` | 明确配额，别让应用猜 | 见第 1 节第 4 条 |
| `taskset` / 绑核 | 仅裸机且明确 NUMA 拓扑时使用 | 容器内绑核常把进程钉在被限速的核上 |
| `ulimit -n`、MySQL `max_connections` | 与 worker 数对齐 | worker 起来了却连不上库，比慢更糟 |
| 慢查询 / `Server-Timing` | 打开观测再谈优化 | 没有基线的「优化」无法证伪 |

## 4. 三道边界（规矩 T）

四个维度看似是四件事，缺的都是同一类东西——**边界**。规矩 T 固化成三句话：

1. **不越界**：应用代码不得出现 CPU 亲和性、线程 / 进程池、fork、优先级调度等调用；这些只写在 §3 的部署清单里。
2. **不猜**：性能结论只来自 `php tools/bench.php` 的可重跑文本输出；禁止「感觉快了」，禁止用截图对比（规矩 A）。
3. **不隐形**：每个响应自证工作量（`Server-Timing`）；预算超限必须留痕；**开关关闭与开启业务语义完全一致**（除传输编码外），优化不许改变结果。

> 三句话分别对应 `22a`、`22b`、`22c` 三组守卫。规矩写在 `CONVENTIONS.md`，每条都有可执行断言，不是文档承诺。

## 5. 可选增强包：做了什么、没做什么

位置 `plugins/Performance/`，通过钩子接入 `kernel.shutdown`（渲染后唯一可编程出口），**`core/` 一个文件没动**：

| 做 | 实现 | 效果 |
| --- | --- | --- |
| 弱 ETag + `304 Not Modified` | `ResponseEconomy` | 重复请求的响应体降到 0 字节 |
| gzip（≥ 阈值且客户端声明接受） | `ResponseEconomy` | 减少传输字节，不触碰业务 payload |
| `Server-Timing: sql;desc="N queries";dur=X` | `PerformanceBudget` | 每个响应自带工作量证据 |
| 预算超限留痕 | `PerformancePlugin` → `kernel.trace` | 慢了会被日志系统记下，而不是等用户报障 |

| 不做 | 理由 |
| --- | --- |
| 缓存 `decide()` 结果 / 带身份的响应 | 规矩 M：只缓存基础数据读取；策略钩子可能带请求级条件，缓存最终结果会绕过收紧策略 |
| 写文件缓存、跨请求共享缓存 | 列入 v1.0；当前只做**无状态**的协商缓存，不引入失效面 |
| 常驻运行时 / 自适应 worker 池 / 自动调参 | 违反规矩 B 与 §1 的判断 |
| 改 CPU 亲和性 / 线程 / 进程优先级 | 见第 1 节 |

`config.performance.enabled = false`（默认）时 `register()` 直接返回，**一个钩子都不注册**。开与关的差别只有响应头与传输编码，`body` 解码后与关闭时逐字相同——这是 `22c` 守的语义等价。

## 6. 对比数据（`php tools/bench.php` 的一次真实运行）

> 全部数字由工具真实执行产生；**没有估算值、模拟值、截图**。
> 数值会随机器负载小幅波动，重跑 `php tools/bench.php` 即可复核；方向由机制决定，不随波动改变。

### 6.1 应用层治理：开关关 / 开

口径：5 个 GET 路径 × 12 轮 = 60 次请求，每轮新建 `Kernel`（真实每请求重建）；开启组第 2 次起带 `If-None-Match` 协商；语义等价在剔除每请求唯一 `request_id` 后逐字比较。

| 指标 | 关闭 | 开启 | 变化 |
| --- | ---: | ---: | ---: |
| 传输字节 | 190,908 | 26,450 | **−86.1%** |
| 200 / 304 | 60 / 0 | 49 / 11 | — |
| gzip 次数 | 0 | 48 | — |
| SQL 条数 | 2,520 | 2,520 | **0（服务端计算未变）** |
| 语义不一致 | 0 | 0 | — |
| 每请求中位数 ms | 3.780 | 3.646 | −3.5% |
| 每请求 P95 ms | 8.540 | 7.570 | −11.4% |
| 服务端总耗时 ms | 292.42 | 288.67 | −1.3%（噪声内） |

**读法**：字节下降是机制决定的（gzip + 304），稳定可复现；SQL 条数完全一致，说明这个包**没有减少服务端计算**；耗时差异落在噪声内，不作为收益宣称。把「传输优化」写成「网站变快」是不诚实的。

### 6.2 部署层：同一份代码，只改服务器配置

环境实测：PHP 8.3.6；`nproc` = **32**；`/sys/fs/cgroup/cpu.max` = **`400000 100000`**（配额 **4 核**）。

| 对照 | 口径 | 结果 |
| --- | --- | --- |
| opcache 关 / 开 | 单进程 200 次请求，5 次取中位数 | 463.28 → 461.96 ms（−0.3%，**方向会翻转，不纳入结论**） |
| `taskset -c 0`（1 核） | 4 并发 worker × 80 请求，整体墙钟 | 970.16 ms（基线） |
| `taskset -c 0-3`（4 核） | 同上 | 343.08 ms，**−64.6% / 2.83×** |
| `taskset -c 0-31`（放开可见核） | 同上 | 294.09 ms，**−69.7% / 3.30×** |

两条站得住的结论：

1. **给足可用核数比什么都有效**：1→4 核接近 3 倍加速。
2. **绑核反而更慢**：钉在固定 4 个核（343 ms）比放开可见核（294 ms）还慢约 17%。容器里 cgroup 配额 4 核与可见 32 核不一致，应用按 `nproc` 去「动态分配核心」或手工绑核，都会把自己钉在被限速的一侧。
3. opcache 在 CLI / 单进程模型下没有稳定收益（多次重跑在 −3.7% ~ +4.7% 间翻转）。它的收益属于 FPM 长驻模型 —— **这正说明配置效果依赖运行模型，只能实测，不能凭直觉**（规矩 T：不猜）。

### 6.3 过程中挖到的真实发现：每请求 `request_id` 会让协商缓存失效

API 信封按 [`docs/api/SPEC.md`](api/SPEC.md) 带每请求唯一的 `request_id`（链路追踪）。基准里 4 个 API 路径**一次 304 都没命中**，只有不含该字段的首页稳定命中 11/12 次。

这不是缺陷，而是 ETag 的**正确安全行为**：内容变了就不命中，绝不会把带旧追踪号的响应发给新请求。真正的教训是——想让 API 也可缓存，正确做法是把 `request_id` 从响应体移到 `X-Request-Id` 响应头（追踪元数据本就该在头里），而不是在插件里「猜字段剔除」。该项列入 **v1.0**，本版不假装完成，也不为此改动 API 契约与既有守卫。

## 7. 明确不做

| 不做 | 理由 |
| --- | --- |
| 新增第 18 个系统层 | 三问法三条不成立；层数已 17，加层不是成就是负债 |
| 核心里的「性能模块」 | `core/` 24/24 已满（规矩 D），且核心零业务（H2） |
| 自动检测 CPU 核数并调 worker | 见 §1 第 4 条，会读错数且有副作用 |
| APM 代理 / 采样 profiler | 第三方服务与常驻采集，超出纯原生栈边界 |
| 用「平均响应时间」下结论 | 只看均值会掩盖长尾；基准同时给中位数与 P95 |
| 跨请求共享缓存 / 文件缓存 | 会引入失效面；当前只做无状态协商缓存，列入 v1.0 |
| 为缓存改写 API 信封的 `request_id` | 会牵动 SPEC / 文档 / 状态追踪，见 §6.3；本版不动既有契约 |

## 8. 守卫（10 项新增，全部可重跑）

| 组 | 断言 | 守的是哪条边界 |
| --- | --- | --- |
| `22a` 边界 | 生产代码零 CPU 亲和性 / fork / 常驻运行时调用；层数仍 17、`core/` 仍 24；部署参数只在文档、开关默认关闭 | 不越界 |
| `22b` 响应经济 | 关闭零增强头；ETag 形状 / gzip 解码逐字等价；304 body 归零且不残留编码头；带身份或非 GET 不协商 | 不隐形 · 语义等价 |
| `22c` 预算与等价 | 阈值边界不超限、超项分别留名；超限留痕且响应头标注；关闭零钩子、开启挂渲染后出口、body 逐字相同 | 不隐形 |

加上原有 240 项，全量 **250 passed, 0 failed**（50 个分组文件）；职责审计 **0 违规 / 0 孤儿协作**。

## 9. 一句话

**没有新增一个系统层、没有动 `core/` 一个文件；把「动态调核」还给部署层，把「性能」从一句口号变成一组能重跑、能被守卫拦下的数字。**
