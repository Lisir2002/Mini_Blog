# 评论互动与治理

> 代码：`systems/Comment/`；接口：`API-COMMENT-006 … 009`；守卫：`tests/groups/37-comment-interactions.php`、`tests/groups/37b-comment-interactions-runtime.php`。

v0.29 之前，评论层能做的只有「发、删、审、读树」。点赞数与举报数从未存在，
`editable` 是列表里一个恒为 `true` 的字段 —— 前端照着它渲染「编辑」按钮，
点进去才发现根本没有编辑接口。这是典型的空头支票：字段存在、语义是假的、
没有任何地方会报错。

这一轮补齐四件事：**互动主体、幂等互动、编辑治理、审核队列**，
外加一条默认关闭的写入节流。目标不是「功能变多」，而是把
「谁做的」「做了几次」「能不能做」变成可判定、可重跑的事实。

## 1. 互动主体：先解决「谁」

所有去重、阈值、节流都以一个稳定、不可逆、定长的键为前提：

| 优先级 | 来源 | 键 | 为什么 |
| --- | --- | --- | --- |
| 1 | 登录身份 `user_id` | `u:<id>` | 客户端传什么都改不了，换 IP / 换浏览器仍是同一人 |
| 2 | 客户端 IP | `i:<sha256(ip\|root) 前 24 位>` | 与既有评论写入同口径，不存明文 IP |
| 3 | 前端匿名标识 `visitor_id` | `v:<sha256(...) 前 24 位>` | 匿名且无 IP 透传时唯一可用的稳定标识 |

`CommentActor` 把解析分成两条：

- **`resolve()`（严格）**：点赞 / 举报用。三者都拿不到时抛 `42201`，明确告诉调用方
  「请登录，或给一个稳定的 `visitor_id`」。
- **`keyOrNull()`（宽松）**：列表与节流用。拿不到就返回 `null`，不阻断读取 ——
  发评论允许匿名是既有能力，节流不能因为「这次没带 IP」就把 CLI / 本机测试 /
  反向代理漏透传全部变成 429。

为什么不退化成统一的 `anonymous` 键：那样两个人点赞只算一次，返回 `changed=false`、
计数不变，看起来完全像幂等生效了，实际是主体丢失。这类错误不会让任何请求失败，
只会让数字安静地错 —— 正是本项目要消灭的那一种。

`visitor_id` 有长度上限（128 字节），超长直接拒绝；键长恒 ≤ 40 字符，与台账列宽一致。

## 2. 点赞：幂等由数据库保证

台账 `comment_votes` 用 `(comment_id, voter_key)` 联合主键，写入走 `INSERT IGNORE`、
取消走 `DELETE`，`changed` 由受影响行数判定。重复点赞返回 `changed=false` 且 `likes` 不变，
不需要先查再写，并发下也不会重复计数。

只有 `published` 评论能被点赞；对 `pending` / `hidden` / `spam` / 已删除评论返回 `40914`。
理由很实际：给一条还没公开、或已被版主隐藏的评论刷赞，既没有展示意义，
也会把审核队列的排序带偏。

## 3. 举报：阈值按「独立人数」而非次数

`comment_reports` 同样是联合主键，同一主体重复举报不累加，`changed=false`。
达到 `comment.report_threshold`（默认 `3`）时，把 `published` 打回 `pending`，
并 emit `comment.auto_hidden`。三个边界：

- **只对 `published` 生效**。已经是 `pending` 的评论不重复下架；`hidden` / `spam` / `deleted`
  也不动 —— 否则一条新的举报会推翻版主已经做出的审核结论。
- **只有 `changed=true` 才可能触发**。重复举报不会把阈值一次次重新触发，
  评论不会在「下架 / 再下架」之间抖动。
- **`threshold <= 0` 表示关闭自动下架**，计数与台账照常记录，站点主可以只收集不动作。

举报原因走白名单（`spam / abuse / offtopic / other`），未知值 `42201`，
不静默归到 `other` —— 拼错的原因值如果悄悄被收下，日后按原因统计时永远查不出问题。

## 4. 编辑：窗口、作者、乐观锁、内容守卫

| 判定 | 结果 | 理由 |
| --- | --- | --- |
| 已删除 / 非 `pending\|published` | `40914` | 不能借编辑把一条已下架的评论改回可见 |
| 不是作者本人 | `40301` | 管理员也不例外：编辑是作者修正自己的话，不是审核权限 |
| `created_at` 缺失或为未来时间 | `40912` | 时钟漂移 / 导入数据不能变成「永远可编辑」 |
| 超出窗口 | `40912` | 窗口从 `created_at` 起算，**编辑不续命** |
| `expected_edit_count` 与库内不一致 | `40913` | 两个编辑同时提交，后到的必须刷新而不是静默覆盖 |

窗口不续命是关键：若从 `edited_at` 重新起算，每改一次就延长一次，
「发布后十分钟内可编辑」会变成永久可编辑。策略层 `CommentInteractionPolicy::editable()`
把时间作为参数注入（不内部读 `time()`），窗口边界因此能被表驱动守卫穷举，
不需要 `sleep`。

编辑正文必须再过一次 `CommentGuard`。新开一个写接口却复用不了既有校验，
就是给长度 / 链接数 / 控制字符检查开了一道后门：发表时挡住的内容，改一个字就能存进去。

`editable` 字段现在由同一策略真实判定，不再是恒真的占位值；列表同时返回
`edit_count`（乐观锁版本）与 `edited_at`。

## 5. 审核队列：口径必须在两种存储里逐字一致

队列 = `pending` 待审 **或** 有任一举报，排除已删除，按举报数降序、`id` 升序。
`total` 与 `items` 同口径，`limit` 上限 200，多读一条判断 `truncated`。

台账比主表活得久（卸载时一起清理，但异常残留仍可能）：指向不存在评论的
孤儿行直接跳过，不渲染成幽灵条目。

MySQL 版用一条 `LEFT JOIN` + 子查询聚合；内存降级版首版只遍历「有举报的评论」，
于是降级后纯 `pending` 那一批会凭空消失 —— 「没有待审」和「这个功能在降级下少了一半」
长得一模一样。修法是让内存版也以主表为准遍历（`MemoryCommentStore::allRows()`），
两种实现由守卫逐项比对结果。

## 6. 列表补计数：一次批量，不随条数增长

`comment.present_many` 过滤器把整页 id 一次性交给 `countsFor()`，
三条聚合 SQL 补齐 `likes / reports / liked / reported`，而不是每条评论查一次。
守卫用一个计数探针断言：四十条评论只调用一次。读路径也不因互动层缺席而 500 ——
钩子没挂上时列表照常返回，只是不带这些字段。

## 7. 写入节流：默认关闭，且只扣「真正通过校验」的请求

复用 `systems/Api/RateLimiter` 的 `flock` 原子读改写，按互动主体分桶，
与全站 API 限流互不挤占。两个决定：

- **默认 `false`**。阈值是站点主的业务决策（是否开放匿名评论、站点规模），
  框架默认开启会悄悄改变既有写入行为。
- **计数放在所有校验通过之后、落库之前**。空正文、超长、文章不存在、父评论不合法
  这些失败请求不该占用额度；否则「空正文应 42201」会先被 `42903` 抢答，
  守卫开始怀疑断言，而不是怀疑实现。

同一账号换 IP 仍共用额度，这是刻意的：`CommentActor` 优先取 `user_id`，
否则换一次出口 IP 就能刷一轮评论。匿名不同 IP 才是独立额度。

## 8. 实现中抓到的真问题

1. **`register()` 里用了未绑定的 `$kernel`**。装配时 `Call to a member function
   hooks() on null`，整站启动失败。改为 `$this->kernel`；这类 fatal 只有在
   真正走一遍装配路径时才会显形，静态读代码看不出局部变量没绑。
2. **冒烟脚本没开 `api.expose_write`**。不同 IP 模拟不同主体时，既有写接口公网边界
   先返回 `40302`，评论根本没建成，后续断言全部连锁失败在 `id=0` 上。
   这是测试站点配置问题，不是实现缺陷 —— 但如果不查清楚，很容易误判成互动层坏了。
3. **内存降级队列漏掉纯 `pending`**（见第 5 节）。
4. **节流多建了一层子目录**。首版把 `RateLimiter` 的根设成 `$root . '/comment'`，
   可计数文件名是 `hash(key)`，而所有评论节流 key 都带 `comment:` 前缀，
   天然已经分桶；多建目录只会留下一个未登记的目录。改回 `$root`。
5. **节流默认开启且放在校验前**。既有内容守卫里「空正文应 42201」变成 `42903`，
   全量守卫立刻报红。改为默认关闭并把 `assertThrottle()` 移到所有参数 / 内容 /
   文章 / 父评论校验之后。
6. **运行时守卫误以为换 IP 会换主体**。断言「不同主体不应共用额度」失败，
   查下来是实现正确、断言写错了：登录身份优先正是为了防刷。改为正向断言
   「同一账号换 IP 仍应被节流」，再用匿名不同 IP 测独立额度。

## 9. 已知边界

- 匿名主体依赖 `visitor_id` 的稳定性；清 Cookie / 换设备会被视为新主体，
  这是匿名去重的固有上限，不做设备指纹。
- 自动下架只改变状态，不删除台账；版主放行后若再次达到阈值，
  需要新的独立举报才会再次触发。
- 节流基于本地文件，多实例部署需换共享存储（与全站限流同一条边界，见规矩 T）。
- `comment_votes` / `comment_reports` 没有外键：表前缀是多站点隔离手段，
  外键名 schema 级唯一会撞名；孤儿由 `RelationRegistry` 与
  `php tools/data.php verify` 巡检，卸载时随主表一起清理。
- 契约 `CommentInteractionStoreInterface` 放在 `systems/Comment/` 内部，
  不进 `core/Contracts` —— 它是系统层自己的实现选择，不是全站契约；
  `core/` 未新增文件。
