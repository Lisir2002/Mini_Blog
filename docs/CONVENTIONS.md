# 工程规矩（立规矩）

> 这份文件是项目的**协作约定**，不是设计文档。
> 每条规矩都必须配一条**可执行的守卫**，否则视为没立住。
> 新增规矩必须写进本文件，并同时补上 `tests/run.php` 里的对应断言。

## 规矩 A · 验证性截图不存活三轮对话

**原文**：验证性截图不存活三轮对话，否则过期图过多影响判断。

**解释与执行口径**：

| 项 | 约定 |
| --- | --- |
| 适用范围 | 用于验证的截图 / 预览快照 / 界面截屏（测试截图、页面预览图、报错截屏） |
| 存活期 | 自产生它的那一轮对话起算，**最多 3 轮**；第 4 轮起视为**过期** |
| 过期处置 | 过期图一律**不得再作为判断依据**，不得引用、不得据此下结论、不得拿来对比新旧状态 |
| 需要复核时 | 重新截取，或改用**可复现的文本证据**：测试断言输出、HTTP 响应体、`php -l` 结果、文件 diff |
| 长期证据 | 只有文本化、可重跑的证据允许进入设计文档与结论；截图不入库、不写进文档 |

**本项目的默认验证方式**（因此天然符合这条规矩）：

```bash
php tests/run.php                    # 断言输出，文本、可重跑
php -l <file>                        # 语法结论
curl -i http://127.0.0.1:8080/...    # 真实 HTTP 响应头与响应体
```

本轮全部验证均采用上述文本证据，**未使用任何截图**。

**守卫**：`tests/run.php` 中所有断言均输出文本结论并在退出码上体现；规矩本身由代码评审清单核对（见规矩 E）。

## 规矩 B · 纯原生技术栈（硬约束 H4）

**原文**：项目设计不允许出现类似 Twig 这种框架出现，我们纯粹原生 PHP ＋ HTML（CSS＋JavaScript）＋ MySQL 自研。

**禁止清单**（静态守卫会逐项扫描全项目）：

- 任何模板引擎：`Twig`、`Blade`、`Smarty`、`Plates`、`Latte`、`Mustache/Handlebars` 服务端渲染
- 任何 PHP 框架 / 全栈依赖：`composer.json`、`vendor/`、`vendor/autoload.php`、`illuminate/*`、`symfony/*`、`slim/*` 等
- 任何 `.twig` / `.blade.php` / `.tpl` 模板文件
- 任何前端框架编译链（构建产物可存在，但框架本体不得参与服务端渲染）
- 任何 ORM / 查询构造器；数据访问只用 `PDO` + 原生 SQL

**允许清单**：

- PHP 自身即模板语言：主题模板是 `.php` 文件，用 `include` + `<?= ?>` + 原生 `foreach / endforeach`
- 输出转义统一走 `SecurityGuardInterface::escape()`，不依赖模板引擎的自动转义
- 样式与交互由主题 / 独立页包自带的原生 CSS / JS 承载
- 依赖仅：PHP 标准库 + `pdo_mysql`

**主题模板示例**：`themes/Bare/templates/page.php` 是原生 PHP 模板，`BareRenderer` 只做 `ob_start() + include`，不拼 HTML 字符串、不调用任何模板引擎。

**守卫**：`tests/run.php` 第 5 组「原生栈守卫」扫描全项目文件名与源码关键字；命中即失败。

## 规矩 C · 一个接口 = 一份规范化操作文档（硬约束 H5）

**原文**：程序的各项操作需要规范化接口，并且一个接口对应一份规范化操作文档。

| 项 | 约定 |
| --- | --- |
| 单一事实源 | `api/registry.json`；文档由 `php tools/gen-api-docs.php` 依据清单生成 |
| 1:1 | 清单里每条接口必须有且仅有一份 `docs/api/<ID>.md`；反过来，任何 `API-*.md` 必须能对应清单条目 |
| 文档必备章节 | 8 节固定：接口标识 / 功能与适用场景 / 请求规范 / 响应规范 / 错误码 / 调用示例 / 幂等性与副作用 / 变更记录 |
| 唯一性 | 接口 ID、`method + path`、`operation` 三者各自全局唯一；注册表构造时强校验 |
| 修改流程 | 先改清单 → 重新生成文档 → 跑守卫测试；**禁止手写文档** |
| 规范来源 | `docs/api/SPEC.md`（借鉴 OpenAPI 3.1 / RFC 9457 / Azure REST / Google AIP，均为自研实现） |

**守卫**：`tests/run.php` 第 6 组逐条检查 1:1、章节齐全、编号与路径一致、无孤儿文档、无重复定义。

## 规矩 D · 核心轻量预算

`core/` 只允许放契约接口与装配基础设施，PHP 文件数上限 **24**（当前 24，**已达上限**）。核心变胖就是第一性原理被破坏的第一个信号。后续新增能力一律进 `systems/` 或走钩子，不得再加契约文件；`themes/` / `plugins/` / `pages/` 只承载呈现与业务包。

**守卫**：`tests/run.php` 静态统计 `core/` 下 PHP 文件数。

## 规矩 F · 写接口必须鉴权，且默认不暴露公网

**来源**：决策 7（接口 `auth` 从声明变成执行）与安全边界「Headless 写接口边界」。

| 项 | 约定 |
| --- | --- |
| 清单声明 | 每个接口必须声明 `auth`：`public` / `user` / `admin`；不声明按 `public` 处理 |
| 执行 | 分发器在**参数校验之前**通过 `ApiAuthenticatorInterface` 校验令牌与角色；未认证 `40101`、令牌无效 `40102`、角色不足 `40301` |
| 公网边界 | 所有非 GET/HEAD/OPTIONS 操作默认仅本机来源可调用；公网来源一律 `40302`，除非显式设 `config.api.expose_write=true` |
| 令牌 | 明文令牌只在签发响应中出现一次；库里只存 SHA-256 摘要，带过期与撤销标记；CSRF 令牌落库、过期、一次性使用 |
| 演示凭据 | `admin/admin123` 仅用于本地原型，不得进入生产配置；口令、签名密钥必须由环境注入 |

**守卫**：`tests/run.php` 第 9 组逐条验证 40101 / 40102 / 40301 / 40302、令牌落库只存摘要、CSRF 一次性、CSP 由配置注入。

## 规矩 G · 样式与脚本只存在于承载包（v0.6 由规矩 J 收紧）

**来源**：决策 3（后台 UI 可卸载）、决策 4（独立页可自带 CSS/JS）与 H1 零呈现。

> **v0.6 修正记录**：v0.5 的 G 允许 `pages/<包>/assets/` 与 `plugins/<包>/assets/`，并用 `standalone` + `render.should_render` 让后台绕过站点主题。用户指出「后台的布局样式一样是需要过主题系统的」——这条口子意味着框架里**存在一条不经主题系统就产出样式的合法路径**，「所有样式都来自主题」便不是全称命题。故 v0.6 立规矩 J 收紧：**CSS/JS 只允许存在于 `themes/`**，独立页不再持有任何模板或资源。下表保留旧约定仅作变更对照。

| 项 | v0.5 旧约定 | v0.6 现行约定（规矩 J） |
| --- | --- | --- |
| 允许位置 | `themes/*/`、`pages/*/assets/`、`plugins/*/assets/` | **仅 `themes/*/`** |

**守卫**：`tests/groups/05-native-stack.php` 断言全项目 `.css/.js` 均在 `themes/`；`tests/groups/11-packages.php` 断言独立页零模板零资源、无主题时后台亦为纯 JSON、bare 主题的后台样式逐字来自主题目录。

## 规矩 H · 单文件不允许职责职权过重

**原文**：单文件不允许职责职权过重。

「过重」不靠主观判断，而由 `tools/audit-responsibility.php` 静态量测。指标全部可复现，策略数据放在 `tools/audit/concerns.json`（策略是数据而非代码，避免审计器自审时把关键字字面量误判成自身职权）。

| 指标 | 定义 | 违规条件 |
| --- | --- | --- |
| `sloc` | 有效代码行（剔除空行与整行注释） | 超过所在层预算 |
| `classes` | 单文件类 / 接口 / trait / enum 数 | `> 1`，即 1 文件 = 1 个责任主体 |
| `public_methods` | 公开方法数 | `> 20`，对外承诺过宽 |
| `fan_out` | `use` 语句数，反映协作面宽度 | 超过所在层预算 |
| `concern_span` | 同时命中的业务职权域数：持久化 / 文件系统 / 呈现 / 安全 / 校验 / HTTP | `≥ 4` 直接违规；`= 3` 且体积超预算 80% 违规（组合规则） |

## 规矩 I · 相互协作必须得到全方位验证

**原文**：相互协作必须得到全方位验证。

接口越多、可插拔单元越多，协作面越容易「看起来都连上了、实际悄悄断链」。这里把「全方位」定义为**四个维度同时满足**，缺一不可：

1. **存在性** —— 协作两端都真实存在，无悬空引用（`use` 的类、契约的实现者、裁决型事件的消费者）。
2. **一致性** —— 声明与实现对账：依赖声明 ↔ 拓扑顺序、operation ↔ 执行者 ↔ 文档 ↔ OpenAPI、磁盘清单 ↔ 状态文件。
3. **运行时贯通** —— 不是静态连上线就算，要真的跑一次跨系统链路并观察结果。
4. **故障注入** —— 故意断链（替换实现、停用被依赖层、缺执行者、拔 DSN、篡改签名），验证能被**明确发现并规范化处理**，而不是静默降级。

**8 类协作矩阵**（定义在 `tools/audit/CollaborationGraph.php`，报告里带 `guard` 字段）：

| 编号 | 协作面 | 两端 | 静态证据 | 运行时 / 故障注入 | 守卫 |
| --- | --- | --- | --- | --- | --- |
| C1 | 契约面 | 接口 ↔ 实现 ↔ 容器绑定 | 13 个契约接口文件均有实现者（容器运行时绑定 10 个，`RendererInterface` 等按主题按需绑定） | 全部 `resolve()` 成功；把内容契约换成内存实现后首页数据仍贯通；覆盖留痕 | C1 |
| C2 | 装配面 | `system.json` requires ↔ 拓扑顺序 | 逐条对账 | 停用被依赖的 `database` → 明确报「依赖未满足」 | C2 |
| C3 | 事件面 | emit/apply 生产者 ↔ on/filter 消费者 | 3 个裁决型事件必有消费者 | 自定义 filter 确实被 `renderStage` 询问 | C3 |
| C4 | 接口面 | operation ↔ 执行者 ↔ 文档 ↔ OpenAPI | 33 条四方 1:1 | 新建未注册执行者的注册表 → `50101`；清单响应示例与真实响应逐字段对账 | C4 |
| C5 | 装卸面 | 磁盘清单 ↔ 状态 ↔ 装载裁决 ↔ 验签 | 单元路径存在、版本对账 | `package.enabled` 裁决点存在；`core` 不可卸载 | C5 |
| C6 | 呈现面 | 路由 ↔ 布局槽位 ↔ 主题渲染 | 主题绑定状态、`theme.layouts` 自报 | 后台走主题 admin 布局；主题缺该布局时退化为纯数据 | C6 |
| C7 | 数据面 | 契约 ↔ 真实表 ↔ 读回 | `system.info` 与 `Db::connected()` 对账 | 拔 DSN 回退内存实现且首页仍有数据 | C7 |
| C8 | 编排面 | 编排者 ↔ 7 个协作者 | `collaborators()` 齐备 | `install` 全链路 `lifecycle.collab` 轨迹覆盖 7 个角色；状态机与验签器脱离编排者独立验证 | C8 |

**C9 是规矩 E 的强化**：`check()` 登记每条用例名，C9 遍历矩阵并断言每一类都有**实际执行过**的守卫（名字前缀核对），同时断言审计零违规、零孤儿、扫描文件数自洽。这样「文档写了协作、测试却没测」会被直接拦下。

**报告不过期**：`tests/run.php` 每次运行都调用 `Auditor::run()` 重新计算并刷新报告——本轮正是 C9 抓到了「新增测试文件后报告过期」的真实缺陷，才把审计引擎改成 CLI 与测试共用一份实现。

## 规矩 J · 呈现权完全归主题系统（后台不例外）

**原文**：后台的布局样式一样是需要过主题系统的。

**为什么必须改**：v0.5 把 `/console`、`/toolbox`、`/install` 做成自带 CSS/JS 的 standalone 独立页，看起来是「高度自定义」，实际是第一性原理的后门。只要存在一条不经主题就能产出样式的合法路径，「主题系统无主题时无任何样式、所有样式都来自主题」就不是全称命题，而是「除了后台之外」。**修法不是给后台再补一套主题，而是把「布局」从「页面」里剥离出来**。

| 项 | 约定 |
| --- | --- |
| 独立页职责 | 只声明路由、产出结构化数据（`title` / `blocks` / `items`），**零 HTML 模板、零 CSS、零 JS** |
| 布局意图 | `page.json` 的 `layout` 字段（`site` / `admin` / `tool` / `install`），由 `PageSystem` 经 `render.layout` 裁决点注入 |
| 主题职责 | 主题包持有全部布局模板（`templates/*.php`）与资源（`assets/*.css|js`），并通过 `theme.layouts` 自报可用槽位 |
| 呈现裁决 | `ThemeSystem` 订阅 `render.should_render`：主题未声明的布局一律不渲染；`RenderInterface` 未写 body 时核心退化为纯数据 |
| 零兜底 | 主题没提供某布局 → 该页输出纯 JSON，**绝不偷偷给一份默认后台样式**；无主题时连后台也零标签零样式 |
| 语义变更 | `standalone`（绕过主题）已废弃，重定义为「请求专属布局槽位」，决定权在主题 |

**守卫**：`05` 组（CSS/JS 只在 `themes/`）、`11` 组（独立页零模板零资源 / 无主题后台为 JSON / bare 后台样式来自主题 / bare-html 后台退化）、`13b` 组（`render.layout` 确被询问）。

## 规矩 K · 权限系统：三层权限与不可提权的扩展点

**原文**：补充权限系统的设计（用户权限，文章权限，系统权限等等）。

**定位**：权限不是「用户系统里的一个字段」，而是横切所有系统层的授权决策面。放用户系统里会让内容 / 装卸 / API 都反向依赖用户系统，违背「系统层一律平等」。故作为**第 12 个系统层**接入，核心只提供 `AccessControlInterface` 询问点，不认识任何具体权限名。

| 层 | 回答的问题 | 实现 |
| --- | --- | --- |
| 用户权限（主体 / who） | 你是谁、属于哪个角色 | RBAC：`permission_roles` + `permission_grants`，支持 `*` 与 `content.*` 前缀通配；`*` 是**显式授予、可撤销**的，不存在硬编码超管 |
| 文章权限（客体 / what） | 这一篇能不能读 / 改 / 发 | `permission_acl` 资源级授权 + 文章状态（published / draft / private / pending）；经 `content.visible` 钩子过滤列表，内容层不硬依赖权限层 |
| 系统权限（操作 / action） | 这个操作能不能做 | 各系统层用 `permissions.json` 自报权限点（同名冲突 fail-fast）；接口清单 `permission` 字段绑定；契约覆盖走 `contract.override` 裁决点留痕 |

**三条硬约束**：

1. **默认拒绝（fail-closed）** —— 决策三态 `allow / deny / abstain`；未声明的权限点、匿名、无策略一律 `abstain`，`allows()` 恒为 `false`。权限层缺席时回退 `DenyAllAccessControl`。
2. **扩展点不得提权** —— `permission.decide` 钩子只能把 `allow` 收紧为 `abstain` / `deny`，任何 `abstain → allow` 的尝试一律忽略。插件与主题永远不能借扩展点给自己授权。
3. **决策必留痕** —— 每次 `decide()` 写 `permission_audit` 表并 emit `permission.decision`，由日志系统消费；留痕失败不阻断决策。

**一个刻意取舍**：`abstain` 不等于「站点全黑」——`content.visible` 对已发布文章仍放行，草稿 / 私有仅作者可见。这样拔库或停用权限层只会关闭写与受限数据，不会把公开站点锁死。显式 `deny` 对**匿名也生效**，这是 13b 组抓到并修掉的真实缺陷。

**守卫**：`13a` 组（三态 / deny 优先 / `*` 可撤销 / 策略不提权 / 留痕 / 声明冲突 / 契约可替换）、`13b` 组（API 执行 / 文章过滤 / public 可选身份 / 契约覆盖 / 拔 DSN 回退）、`13c` 组（角色继承并集 / 环路裁决 / 撤销传播 / 接口贯通）、`13d` 组（缓存失效 / 不绕过策略钩子 / 字段级权限 / 协作对账）、`14a`–`14d` 组（页面分级 / 策略不可提权 / 契约覆盖鉴权 / 身份载体同源）。

**v0.7 深化（规矩 K 的延伸，不新增规矩）**：角色继承用 `permission_role_parents` 边表 + 决策时展开，写入前拒绝自环 / 成环 / 深度超限；决策缓存只缓存基础数据读取，**绝不缓存 `decide()` 最终结果**，所有授权写操作显式 `flush()`；资源 ACL 增加 `field` 维度，`decide()` 签名不变。三者全部落在 `systems/Permission/`（新增 `RoleGraph` / `PermissionCache` / `AclMatcher` 三个单一职责协作者），`core/` 仍 24 个 PHP、13 个契约，权限点仍 20 个。v0.8 已落地装配期契约覆盖的运行时身份授权台账与页面级访问裁决，详见 `docs/ARCHITECTURE.md` 第 24 节。

### 规矩 L · 页面访问策略清单化与契约覆盖运行时身份（v0.8）

**条目**：任何页面的「谁能访问」必须写在 `page.json` 的 `access` 段，不得散落在独立页代码里；裁决统一在 `route.access` 可编程询问点完成，拒绝时短路，页面业务逻辑不执行。裁决复用 API 的两级契约：`ApiAuthenticatorInterface::allows()` 判身份级别、`AccessControlInterface::allows()` 判权限点，权限层缺席 / `abstain` 一律拒绝。策略钩子 `page.access.policy` **只能收紧**（提升 `auth`、追加 `extra_permission`、打开 `local_only`），放宽一律忽略。拒绝响应只产结构化数据 + `deny` 布局槽位，样式同样归主题；主题缺该布局则退化为纯 JSON。未显式声明 `access` 的页面默认 `auth=user`（fail-closed）并告警，公开页必须显式写 `public`。

**契约覆盖**：v0.6/v0.7 装配期覆盖只留痕；v0.8 起 `permission.contract_override.require_grant=true` 时，覆盖必须先由具备 `system.contract.override` 权限的**运行时身份**通过 `API-PERM-012` 登记授权，未授权覆盖 fail-closed 拒绝。授权台账归权限层自建表；`API-PERM-011` 提供装配期实际覆盖与授权台账的对账视图。执行者会再次用同一个决策器复核身份，绕过 `RequestGuard` 直调也不会产生无主授权。

**守卫**：`14a`（清单分级 / 短路 / 双重裁决 / `local_only` / fail-closed）、`14b`（策略不可提权 / 拒绝页归主题 / 留痕 / 身份贯通）、`14c`（授权台账 / 40303 / 纵深防御 / `require_grant` fail-closed / 拔库 / 卸载清理）、`14d`（三种身份载体同源、无效令牌不可区分）。

**边界**：`core/` 仍 24 个 PHP（只改 `Router.php` 增加询问点，未新增文件）、13 个契约；权限点 20 → 23（由 `page` 层自报 3 个）；`core/` 依旧不认识任何权限名与页面类型。

### 规矩 M · 主体可扩展与凭据单一来源（v0.9）

**条目**：新增「谁能拥有权限」的维度时，优先扩展**角色来源**，不得新增决策层。用户组因此只是 `自身 role ∪ 组绑定 role`，决策骨架、`deny` 优先、`tighten()` 一律不动；组绑定的是既有角色，不新增权限名。凭据必须单一来源：页面会话与 API 令牌共用 `wx_user_tokens`、同一套过期与撤销；页面会话只换载体（HttpOnly + SameSite Cookie），只用于页面 `GET/HEAD`，**不能**作为 Bearer 调普通 API；会话自身的管理端点必须在清单里显式声明 `accept_session: true`。缓存只允许缓存基础数据读取，**绝不缓存 `decide()` 最终结果**；换后端（memory / file / 共享存储）不得改变任何决策结果。字段级权限必须读写同构：写路径复用 `decide(..., ['field'=>...])`，任一字段非 `allow` 就整次拒绝，不做部分写入；**读写两条路径必须认同一个资源标识**（本框架统一为 `slug`），否则同一条 ACL 只保护其中一侧，等于没保护。装配期契约覆盖默认 `require_grant=true`，只对已注册系统层自动登记，第三方必须运行时授权。

**守卫**：`15a`（组角色并集 / 撤销与删组立即失效 / deny 优先 / 接口贯通）、`15b`（会话签发与 Cookie 属性 / 只用于页面 GET / 会话令牌不得当 Bearer / 登出与过期 / 明文不外泄）、`15c`（file 后端跨实例 / epoch 失效 / 开关一致性 / 不绕过策略钩子）、`15d`（字段级 deny / 字段隔离 / 部分写入禁止 / 白名单与状态校验 / 读写资源标识一致）、`15e`（默认安全 / 自动登记范围 / 第三方未授权拒绝 / 撤销后复发拒绝）。

**边界**：`core/` 仍 24 个 PHP、13 个契约；新增 12 个协作者全部在 `systems/`；表 11 → 14（分组 3 张，会话复用令牌表）；接口 33 → 39；权限点仍 23。跨主机缓存共享、组嵌套、会话多设备管理列入 v1.0。

### 规矩 N · 身份与授权解耦（v0.10）

**条目**：头衔、等级、经验都是**身份描述**，不是授权依据。任何「凭头衔 / 凭等级放行」的写法都违反规矩 K 的唯一授权入口；若确实要让等级解锁能力，正确做法仍是把等级当成「角色来源」，与用户组同构，而不是在标签上加判断。头衔必须支持站长自定义（标识 / 名称 / 颜色 / 权重 / 展示 / 自动门槛），经验规则与等级门槛也必须由站长定义，系统只校验结构合法性。经验发放必须同时满足四条：流水 append-only、`event_key` 幂等、每日上限截断、写流水与加余额同事务；等级是「经验 + 门槛」的解释结果，必须可重算、可重解释、**只升不降**。头衔自动授予不写授予表（按等级实时并集），手动授予必须显式撤销；两种来源都不得改写角色集合。系统层内部存储协议不得注册进容器，对外只暴露 `*.operation` 与事件。新增守卫必须隔离限流 / 缓存等全局副作用，否则失败信息会指向无关位置。

**守卫**：`16a`（组自定义 / 角色并集 / 撤销即时失效 / 展示属性不改决策）、`16b`（头衔自定义 / 手动授予与撤销 / 等级自动授予 / **授予前后决策一致** / 越权与未知头衔）、`16c`（幂等重放 / 每日上限截断 / 规则停用 / 内容事件自动发放与匿名跳过）、`16d`（门槛边界 / 升级判定 / 只升不降 / 门槛重复与删除后重解释）、`16e`（资料装配 / 可停用 / 无库回退 / 权限点自报与撤销后 fail-closed）。

**边界**：`core/` 仍 24 个 PHP、13 个契约；新增 16 个文件全部在 `systems/Member/`；表 14 → 20；接口 39 → 49；权限点 23 → 28。经验流水无归档策略、排行榜为 `limit/offset`、等级变更不回溯通知、成员层零页面零样式（展示权归主题），均已在文档标注。

### 规矩 O · 验证脚本不入项目（v0.10）

**条目**：调试、冒烟、探针脚本一律写在 `/tmp`，不得落在项目目录。项目内只允许两种可重跑证据：`tests/groups/` 下的守卫，与 `tools/` 下的正式工具。禁止的后缀——`.py` `.sh` `.bash` `.ps1` `.bat` `.cmd` `.bak` `.orig` `.rej` `.tmp` `.swp` `.swo` `.sqlite` `.sqlite3` `.db` `.dump`，以及以 `~` 结尾的文件；`.log` 只允许出现在 `storage/logs/`（运行时日志），`.sql` 只允许出现在 `systems/*/migrations/`（建表迁移）。文件名不得以 `tmp` `temp` `verify` `smoke` `scratch` `playground` `dump` `bak` `debug-` 开头。根目录与 `tools/` 顶层是白名单制：**先改守卫，再改目录**，不允许「先塞进去再补规矩」。守卫文件统一 `NN[x]-kebab-case.php`，不允许在其中夹带非守卫脚本。

**理由**：一次性脚本一旦入库会同时破坏三件事——读者无法区分「产品代码」与「昨天验证用的东西」；体积 / 扇出 / 协作统计被噪声污染，审计结论失真；下一个人会照着它继续写。删除成本永远高于不写进来。

**守卫**：`17` 组（根目录白名单 / 后缀与命名黑名单 / `tools` 白名单 / 守卫命名规范），并配 `.gitignore` 作为版本控制层的兜底。

**边界**：`storage/` 是运行时目录，缓存、幂等、限流、日志都会被写入，但它不是「脚本」，守卫只约束其中 `.log` 的位置；`/tmp` 下的临时脚本不受本规矩约束（本来就短命）。

### 规矩 P · 安装与版本必须可逆（v0.11）

**条目**：安装与版本变更都必须做到「装得进、改得对、退得回」，且每一步都能用磁盘与数据库的事实复核。

安装侧：
- 只允许五步——环境检查 → 数据库 → 管理员账号 → 建表与迁移基线 → 完成并加锁；顺序固定，前一步没有事实依据时不写下一步的状态。
- 只写 `config/local.php`（覆盖层）与 `storage/install.lock`；**绝不改写带注释的 `config/app.php`**，删掉 `local.php` 即回到默认配置。
- 写动作必须携带 `storage/install.token`（0600、仅本机可读的一次性令牌），页面本身 `local_only`；`install.lock` 存在后整个向导返回 404，不再提供任何安装动作。
- 建表复用各系统层 `ensureSchema`，迁移基线复用版本系统台账，安装器不另造一套 DDL。

版本侧：
- 每次变更必须回答三个问题：**库该做什么**（迁移台账）、**文件换到哪**（SemVer 清单）、**失败怎么退**（逆向回退）。
- 升级顺序固定：执行未登记迁移 → 换有版本变化的系统层 → 换 core → 健康门禁；任一步失败按逆序退回，并把失败写进历史。
- 已执行脚本的 checksum 被改动 → 拒绝升级（`40904`），历史不可改写；缺 `.down.sql` → 整批拒绝回退（`40903`），不做「代码退了库没退」的假成功。
- 每次替换前留版本快照，按版本归档、可枚举、可**指定**回退；`keep_releases` 只裁最旧的，当前版本永不裁。快照名必须带时序戳（秒 + 微秒），否则同一秒内的多次快照会让「保留最近 N 份」变成随机结果。
- 首次启动只做**基线登记**（只写台账、不重跑脚本），否则第一次升级会重放建站以来的全部迁移与种子。
- 数据库不可用时降级为内存台账：查询可用，写入明确以 `50004` 拒绝，不允许假成功。

**理由**：安装器与升级器是唯一会同时动「文件 + 配置 + 数据库」的两处代码，也是最容易留下半截状态的地方。把「顺序」「可逆」「证据」写死，比事后写一份排障手册便宜得多；而回退一旦不可用，站长就只剩重装一条路——这正是本框架要消除的成本。

**守卫**：`18a`（升级/回退全链路：迁移 → 单元 → core → 健康门禁 → 快照）、`18b`（checksum 冲突 `40904` / 不可逆拒绝 `40903` / 多快照与裁剪 / 无库降级）、`18c`（五步结构 / 令牌 0600 与 403 / 公网拒绝 / 装完 404）、`18d`（`config/local.php` 0600 与删即回默认 / 管理员幂等 / 台账登记与加锁）。

**边界**：不提供在线下载源包（`source` 必须是已就位的目录）、不做灰度分批、不做升级并发锁（同一时刻只应有一次升级）、不支持跨大版本跳版（要求逐版递增）。健康门禁覆盖 database / tables / contracts / systems / operations 五项，不含业务数据一致性校验。

### 规矩 Q · 状态必须可推导、可行动、可追踪（v0.12）

**条目**：任何面向人的「状态」都必须同时回答四件事，缺一不可：

1. **相位**：`pending / running / waiting / done / failed`；
2. **持有者**：卡在系统（`held_by=system`）还是人（`held_by=user`）；
3. **说明与出路**：`title / message / hint` + 最多 4 个可执行动作；
4. **证据**：业务码、`trace_id`、发生时间、是否可重试。

约束：

- 五态由 `phase + held_by` 组合表达，不得做成五个并列枚举；只有 `waiting` 可以带 `held_by`，只有 `failed` 可以带业务码。
- 状态必须**从事实推导**，不得另存一份与事实并行的布尔；页面级 / 动作级状态随响应返回，只有跨请求长任务才允许落库。
- 长任务写入必须带 `revision` 做 CAS；终态不可回退；过期必须可清理。
- 文案是「键 + 默认中文」，主题可经 `state.copy` 覆写；**外观与可访问性归主题**（错误 `role="alert"`、其余 `role="status"`、进行态 `aria-busy`）。
- 未捕获异常必须走 `kernel.exception` 统一出口；没有消费者时核心只允许输出纯文本 500，不得兜底 HTML。
- 异常原文不得进入界面；SQL、路径、令牌片段只进日志，界面给 `trace_id`。

**理由**：错误码只说明「失败了」，说明不了「进行到哪」「在等谁」「我该怎么办」。这三件事缺失时，用户只能刷新或报障，模型也无法决定下一步；而把状态写成散落各页的布尔值，一年后必然漂移。

**守卫**：`19a`（五态组合 / 业务码 / 动作白名单 / 进度边界 / 不可变 / 文案覆写 / 异常与信封翻译）、`19b`（长任务 / CAS / 终态 / TTL / 安装页真实状态 / 无主题降级 / 主题片段可访问性 / 异常出口 / 停用降级 / 只读接口）、`11`（`kernel.exception` 无消费者即孤儿）。

**边界**：不提供前端状态管理库，不接管轮询；状态系统只给结构与键，长任务轮询由调用方决定频率。

### 规矩 R · 内容互动：所有权清晰、字节不入库、表情不产 HTML（v0.13）

**条目**：评论、附件、表情是三类生命周期不同的数据，必须各有归属，不得塞进内容层：

1. **评论**：关系（`parent_id` / `path` / `depth`）与可见性必须由事实推导；删除必须软删并保留路径，让子回复仍能显示；审核迁移必须走显式白名单，非法迁移一律 `40901`；超过深度上限必须拒绝，**不得静默改挂父节点**。
2. **附件**：元数据入库，字节落盘，两者以 SHA-256 绑定；存储路径**不得包含用户提供的文件名**；上传必须同时通过大小、扩展名白名单、魔数三道校验，文本类另加「无 NUL + 合法 UTF-8」；下载必须每次做授权判定，**不得以「URL 不可猜」替代访问控制**。
3. **二进制通道**：上传 / 下载必须复用与 JSON 接口同一套请求守卫（限流 → 写边界 → 鉴权 → 权限 → 参数），不得单开一条绕过鉴权的旁路；响应必须带 `X-Content-Type-Options: nosniff` 与 `Content-Security-Policy: default-src 'none'`。
4. **表情**：解析必须产出 token 而非 HTML；自定义表情只允许引用本站附件 id，**拒绝任何外链**；正文必须存原文、渲染时解析，删除表情不得改写历史内容；未知短码保持字面量。
5. **协作**：三者之间只通过 core 契约（`ContentRepositoryInterface` / `AttachmentRepositoryInterface`）或钩子（`emoji.parse`）协作，不得直接查询对方的表。

**理由**：这三件事各自都有一类「看起来能跑、实则埋雷」的实现——硬删评论让对话断裂、用原始文件名落盘导致路径穿越、把表情直接拼成 HTML 打开 XSS 面。它们的共同点是：**错误发生在设计层，写再多校验也补不回来**。所以规矩必须约束结构，而不是约束某个函数。

**守卫**：`20a`（树装配 / 路径深度 / 回评约束 / 软删保链 / 审核状态机 / 可见性 / 内容守卫）、`20b`（文件名净化 / 内容寻址去重 / 类型与魔数 / 下载头 / 私有授权 / 软删 / 配额）、`20c`（内置目录 / 解析边界 / 自定义约束 / 删除不改写历史 / 共用入口）；`11`（`emoji.parse`、`attachment.uploaded` 等事件与 operation 必须 1:1 绑定）。

**边界**：不做评论投票、不做附件断点续传与 CDN、不做表情商店；附件字节回收与评论物理清理由独立运维流程负责，不在请求路径内执行。
